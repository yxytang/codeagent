# DeepSeek 20-task Benchmark · 2026-10-21

20 道合成任务、四个配置、每题每组运行一轮，共 **80 次真实 Agent 运行**。模型请求使用同一冻结的 `deepseek-chat` 连接。每次最多 18 个逻辑模型调用、48 个工具调用、32,000 已报告 Token，超出 Token 阈值后不再启动新调用；最后一个在途响应可以越界。

本批 **Prompt Guidance 表现最好**；Full Harness 没有优于 Baseline。本结果不支持组件叠加必然提升完成率的结论。

| 组别 | 原始通过 | 复评通过 | 复评成功率 | 平均模型轮数 | 平均已报告 Token | 平均耗时（秒） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Baseline | 12/20 | 13/20 | 65% | 9.85 | 22,824 | 17.35 |
| Context Manager | 12/20 | 13/20 | 65% | 10.30 | 23,309 | 17.80 |

Prompt Guidance 相比 Baseline 在本批多通过 5 题，成功率高 25 个百分点，平均已报告 Token 少 17.3%。这是单轮观察；四组采样参数相同但不保证输出相同，不能据此直接给出稳定收益或因果结论。

平均值包含失败尝试。耗时不包含私有验收；Token 来自 API usage，不是精确账单。正式批次累计 **1,715,930 已报告 Token、758 次逻辑模型调用、799 次工具调用**。先前冒烟与中止试跑的用量未计入正式批次。

## 为什么复评

`refactor-02` 原验收把仓库 `save()` mock 为返回字符串，并要求旧 `save_items()` 转发该字符串。旧 API 和真实仓库保存方法都返回 `None`，题面只要求保留旧接口并委托仓库，未要求转发哨兵返回值。修订后按真实 `None` 行为检查，同时仍断言仓库确实收到调用。

修订不改变任务目标、初始文件、模型输出或执行预算；只对四份已有候选代码离线重新验收。四组各增加 1 题，旧报告、旧验收、新验收、报告哈希均保留。已核对 **80 份初始文件和任务目标未变、其余 76 条评分记录未变、全部运行指标未变**。

## 测试反馈与失败分析

- 本批 7 次运行出现公开测试命令先失败、后通过的序列；序列本身不等于已经确认修复因果。
- `bugfix-02 / full` 有完整修复证据：首次实现遗漏金额乘 100，测试报告 `12 != 1234`；后续执行消息显示修改换算逻辑，再次运行同一命令通过，最终私有验收也通过。公开测试文件 SHA-256 前后相同，未通过改测试规避失败。
- 复评后的 24 次失败中，19 次是预算耗尽，5 次是运行达到 ready 但独立验收不通过。后者包括列表顺序、直接依赖语义和返回值理解错误。
- 上下文压缩实际触发 21 次，涉及 8 次运行（Context 与 Full 各 4 次）。不能把组件未触发的任务差异解释为压缩收益。
- Skills、MCP 与跨任务历史记忆在本批保持固定或关闭；本对照不能评估它们各自的贡献。每个配置仅运行一轮，样本为小型本地题目，不能当生产任务完成率。
